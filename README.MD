This project serves as a technical demonstration of modern architectural patterns, focusing on strict separation of concerns, domain encapsulation, and high-performance relational querying[span_42](start_span)[span_42](end_span)[span_43](start_span)[span_43](end_span)[span_44](start_span)[span_44](end_span)[span_45](start_span)[span_45](end_span).

## Architectural Overview

The solution strictly adheres to **Clean Architecture** principles, divided into four primary layers: Domain, Application, Infrastructure, and API[span_46](start_span)[span_46](end_span)[span_47](start_span)[span_47](end_span). The dependency rule points exclusively inward, ensuring the core business logic remains framework-agnostic[span_48](start_span)[span_48](end_span).

## Key Patterns & Principles

* **Domain-Driven Design (DDD):** The core features a rich domain model where entities act as Aggregate Roots, encapsulating their invariants[span_49](start_span)[span_49](end_span). Properties have private setters to prevent anemic models, forcing state changes through explicit domain methods[span_50](start_span)[span_50](end_span). To strictly enforce aggregate boundaries, domain entities omit ORM navigation properties and reference related aggregates (`ScheduleBlocks`, `Appointments`, `Staffs`, `Patients`) exclusively by `Guid` identifiers[span_51](start_span)[span_51](end_span)[span_52](start_span)[span_52](end_span)[span_53](start_span)[span_53](end_span)[span_54](start_span)[span_54](end_span).
* **State Machine Logic:** Clinical appointment workflows are embedded within the domain entity[span_55](start_span)[span_55](end_span)[span_56](start_span)[span_56](end_span). Transitions across active, reserved, in-progress, and cancelled states (`AppointmentStatus.Cancelled`) are governed by domain rules, ensuring data consistency across the scheduling lifecycle[span_57](start_span)[span_57](end_span)[span_58](start_span)[span_58](end_span)[span_59](start_span)[span_59](end_span)[span_60](start_span)[span_60](end_span).
* **Command Query Responsibility Segregation (CQRS):** Orchestrated via `MediatR` (`IRequest` and `IRequestHandler`) to decouple state mutation from read-heavy workloads[span_61](start_span)[span_61](end_span)[span_62](start_span)[span_62](end_span)[span_63](start_span)[span_63](end_span). Read operations (`GetDailyAgendaQuery`, `SearchAvailabilityQuery`) bypass domain repositories and EF Core change tracking by querying `ApplicationDbContext` with `.AsNoTracking()` and projecting directly into immutable records (`AgendaBloqueDto`)[span_64](start_span)[span_64](end_span)[span_65](start_span)[span_65](end_span)[span_66](start_span)[span_66](end_span)[span_67](start_span)[span_67](end_span).
* **Explicit Relational Querying & Left Anti-Join Pattern:** Because entities omit navigation properties under DDD constraints, read projections use explicit LINQ query syntax[span_68](start_span)[span_68](end_span)[span_69](start_span)[span_69](end_span)[span_70](start_span)[span_70](end_span). `GetDailyAgendaQueryHandler` executes chained `LEFT JOIN` operations via `DefaultIfEmpty()` across `ScheduleBlocks`, active `Appointments`, and `Patients` to project schedule availability, patient full names (`FirstName`, `LastName`), and clinical NLP summaries (`NlpSummary`)[span_71](start_span)[span_71](end_span). `SearchAvailabilityQueryHandler` combines an `INNER JOIN` on `Staffs` (filtering by `Specialty`) with a **Left Anti-Join** against `Appointments`, materializing empty active appointment groups into `NULL` phantom references via `DefaultIfEmpty()` and applying `where activeApp == null` to return exclusively unoccupied blocks within the requested date range[span_72](start_span)[span_72](end_span)[span_73](start_span)[span_73](end_span).
